# Data in Oneiric

Every data file the application reads, what it holds, where it came from, and how it is checked. Where something a
reader might expect is **not** in the repository, this file says so and says why, rather than leaving a gap that looks
like an oversight.

## Shipped with the application

These files are in `app/public/data/` and are loaded by the browser. All of them are derived data, not raw rasters.

| File | Size class | What it holds | Source | Checked by |
|---|---|---|---|---|
| `sites.json` | 12 KB | 33 library sites: id, name, coordinates, grade, and the published source for the coordinate | Mazarico et al. 2011 via Gläser et al. 2018 Table 1 for the polar points; USGS/NASA region descriptions for the illustrative Artemis III points; NASA NSSDC Apollo Landing Site Coordinates (Wagner et al. 2017, LRO images) for the Apollo sites | Site-library tests; every coordinate carries its citation |
| `ephem/<year>.bin` | about 280 KB per year (18 years, 4.9 MB total) | One row per hour: Sun and Earth unit vectors in the Moon-fixed frame, plus both ranges | JPL Horizons `MOON_ME` vectors, fetched and byte-packed by the pipeline | `npm run validate` against 8,000 held-out Horizons comparisons, max error 0.0061° |
| `skylines/index.json` | 24 KB | The skyline manifest: site, height, grade, terrain product, and file for each stored skyline | Built by `npm run build:skylines` from the LOLA rasters | `npm run validate`, skyline-file check |
| `skylines/<site>-<height>m.bin` | 8.6 KB each (96 files) | Terrain horizon and distance at 1,440 azimuth bins (0.25°) for one site at one observer height | LOLA south-polar DEMs, product 90 (20 m, 80 m, 240 m pixels) | Decoded and compared by the skyline tests; a big-endian read is a deliberate test failure |
| `validation.json` | 24 KB | The recorded result of every check the Method drawer shows: sample count, residual, threshold, date, and engine commit | Written by `npm run validate` | Regenerated by that command; the drawer shows what the file says |
| `horizons-check.json` | 24 KB | Cached per-site Horizons queries: the largest angular difference and the epoch count | JPL Horizons, fetched once per site and stored | Shown only for sites with a cached entry; a site without one says so |
| `artemis-regions.geojson` | 4 KB | Simplified outlines of the nine Artemis III candidate regions | USGS Astrogeology ScienceBase, DOI 10.5066/P1MEQ6UK, simplified in the repository | Region-outline check |

## Reference values used in a comparison

| File | What it holds | Status |
|---|---|---|
| `data/published-illumination.json` | Two published average-illumination values at the Connecting Ridge reference point, each with its paper, raster resolution, stated definition, and a verification flag | **Both rows are unverified.** They were taken from a secondary source, and neither paper has been opened to confirm the figure or its definition. `npm run illumination-compare` prints that state next to every number. |

The comparison these values feed is reported by `npm run illumination-compare`. It compares only at a published
observer height and averaging definition that are both established. Neither is established for these two values, so
the script prints this build's measured figure at every stored height, the spread between them, and claims no pass or
fail. The reason is in the data: at the reference point the annual average runs from 31% at 0 m to 93% at 20 m, so the
observer height alone moves the answer by more than the tolerance the comparison would use.

## Not in this repository, and why

| Data | State | What the application does without it |
|---|---|---|
| LOLA elevation rasters (`data/`, `data-raw/`) | Gitignored: the 20 m product is many gigabytes | Ships the derived skylines instead. The raster-orientation check reports **PENDING** rather than passed, and says no raster is present |
| 5 m near-field rasters | Not supplied | No 5 m horizon is computed or drawn. A circle point with no stored skyline is reported as having none; a near-field skyline is never borrowed from a coarser product |
| Static south-polar hillshade (`app/public/data/basemap/`) | Not shipped: it is built from the gitignored rasters, which are not in this checkout | The map shows the online LOLA shaded-relief tiles from Moon Trek, in the same projection, and says so under the map |
| Skyline per 100 m circle point | Not built: no circle point has a stored skyline | `npm run landing-report` reports every circle point as having no stored skyline and says the share was not computed. Nothing is interpolated from the centre |
| Vertical error value for each product | Documented but not read: the product pages name the `_ERR.TIF` rasters, the rasters are not here | No horizon band is shown. The card names the product and says its error value is not in this build. A missing error is never shown as zero |

## How the data is checked

- `npm run validate` runs the direction, skyline, raster-orientation, skyline-file, observer-heights, and mission-hindcast checks and
  rewrites `app/public/data/validation.json`. The Method drawer shows exactly what it wrote.
- `npm test` includes the decoding, wrapping, and grade tests, and a set of deliberate-sabotage cases.
- `npm run mutation-check` changes one element of the engine at a time and requires each change to break a test.
- `npm run illumination-compare`, `npm run landing-report`, `npm run blocking-report`, and `npm run sensitivity-report`
  print the measured values for the claims the application makes, with the unavailable cases named as unavailable.

## Regenerating derived data

```bash
npm run build:ephem       # fetch and pack the hourly tables (needs network)
npm run build:skylines    # read the LOLA rasters and write the skylines (needs the rasters)
npm run build:basemap     # draw the static hillshade (needs the rasters; writes nothing without them)
npm run validate          # re-run the checks and rewrite validation.json
```

Each of these prints what it wrote, or why it wrote nothing. None of them invents a file to fill a gap.
